# Operations and disaster recovery

How CleverCon is operated, backed up, and recovered. This is a living runbook; it marks what is in place today versus what is recommended before a mainnet deployment.

## The one invariant that bounds every incident

**On-chain is the source of truth for funds.** The vault (CleverVault) holds the money and enforces every release on-chain. Postgres is a queryable mirror, not custody. So even a total loss of the database or Redis cannot lose user funds: balances, locks, and settled payments can be re-derived from the chain via the indexer. Recovery is about restoring the mirror and the operational state, never about recovering money.

## Stateful components

| Component | Holds | Loss impact |
|---|---|---|
| PostgreSQL | users, roles, sessions, API keys, services, tasks, policies (commitment only), payment mirror, indexer cursor, agent delegates (encrypted), agent wallet public keys | mirror + off-chain state; re-derivable from chain + re-auth |
| Redis | cache, BullMQ queues, rate-limit counters, socket.io pub/sub | in-flight jobs and cache; jobs are idempotent and re-enqueueable |
| On-chain (Soroban) | vault balances, locks, per-step release records, nullifiers, policy commitments | the actual funds and enforcement; the durable source of truth |
| `.env` secrets | JWT secret, `DELEGATE_ENCRYPTION_KEY`, admin/deployer keys | see key management below |

## Backups

- **PostgreSQL:** enable point-in-time recovery (WAL archiving) in production, plus a daily `pg_dump` retained 30 days. Nothing in Postgres is unrecoverable (it mirrors the chain), but backups make restore fast and preserve off-chain state (API keys, webhooks, disputes).
- **Redis:** append-only file (AOF) persistence is enabled in `docker-compose.yml` (`--appendonly yes`). Queues and cache survive a restart. A full loss is tolerable: cache rebuilds, and jobs are idempotent (exactly-once settlement is guaranteed on-chain), so re-enqueueing cannot double-pay.
- **Secrets:** `.env` is never committed. In production, hold secrets in a managed KMS/secret store rather than a file, and back up `DELEGATE_ENCRYPTION_KEY` securely (see below).

## Restore procedure

1. Restore PostgreSQL from the latest base backup + WAL (or the newest `pg_dump`).
2. Bring up Redis (empty is fine; AOF restore optional).
3. Start the API, workers, and indexer. The indexer resumes from its cursor (`IndexerState`) and reconciles the vault mirror from chain events. Any cursor gap is re-ingested idempotently (events dedupe on cursor).
4. Verify `/health`, then confirm the admin stats and activation funnel read sane values against the chain.

## Delegate-key recovery

Per-user spending delegates are generated by the platform and stored **encrypted at rest** (AES-256-GCM) in Postgres, keyed by `DELEGATE_ENCRYPTION_KEY`. Recovery rules:

- **Back up `DELEGATE_ENCRYPTION_KEY`** out of band. Without it, stored delegate ciphertexts cannot be decrypted.
- If a delegate key is lost or rotated, a user can **re-provision and re-authorize** a new delegate (register_orchestrator). The vault's policy enforcement means a delegate never holds funds, so rotating one cannot lose money; it only requires the user to re-authorize.
- The user's **agent wallet** (agent-key mode) is never held by the platform (only its public key is stored), so there is nothing to recover server-side; the user controls that key.

## Incident runbook

- **API down:** check `/health`, the process, and the Postgres/Redis connections. The API is stateless, so restart or reprovision freely.
- **Settlement stuck / retrying:** settlement is idempotent by `(task, step)` on-chain; a retry cannot double-pay. Inspect the settlement queue and worker logs; a release that succeeded on-chain but failed to record will reconcile on the next run (see [reconciliation.md](reconciliation.md)).
- **Indexer behind:** it resumes from its cursor and re-ingests idempotently; give it time or restart it. The app reads the mirror, so a lagging indexer shows stale balances, not wrong ones.
- **Queue backlog:** scale worker concurrency (stateless, BullMQ) or add worker instances.

## Observability in place

- **Structured logs** (pino): JSON in production, per-request correlation id (inbound `x-request-id` honored), auth redaction.
- **Tracing** (OpenTelemetry): off unless `OTEL_EXPORTER_OTLP_ENDPOINT` is set; instruments http/express/pg/ioredis.
- **Health**: `/health` on the API.
- **Product**: the admin activation funnel and stats give a first-party view of usage.

## Before mainnet (recommended, not yet done)

- Managed Postgres with PITR + tested restores; managed Redis with persistence.
- Secrets in a KMS, not `.env`; rotation policy for `DELEGATE_ENCRYPTION_KEY` and the JWT secret.
- Alerting on queue depth, indexer lag, error rate, and `/health`.
- A scheduled reconciliation job that re-checks the mirror against the chain.
- An external security audit of the contracts and API (tracked separately).
